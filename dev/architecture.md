# Architecture (maintainers)

Not needed to author diagrams. Describes how the skill is organised so new diagram types can be added without touching the shared parts.

## Layers


## Design system

Every colour, size, font, radius, shadow, icon and text style on a page comes from one token set. A type never decides how something looks, it only says which token or component it uses.

**Layers and assembly.** `assemble_page()` (`layout_engine.py`) fills the placeholders of `shell.html` in this order, which is also the cascade: tokens (`{{TOKENS_CSS}}`, generated by `scripts/tokens.py` from `assets/tokens/default.json` merged with a theme), shared components (`{{COMPONENTS_CSS}}`, `assets/components/*.css`), shell (`shell.css`), then the type's own CSS. Scripts: `{{TOKENS_JS}}`, the shell, the engine, `{{MERMAID_JS}}` (the type's Mermaid reader and writer), the type script. `{{TOKENS_JS}}` defines `TOKENS` (palette, `font.metrics`, `type`, `icon`) and `ICONS` before the shell and the engines. A theme omits any key it does not change; the loader validates it (`tokensVersion` 1) and rejects anything that is not a colour, length, number or an allowed font URL.

**Effects.** `effect` in the tokens holds the shared emphasis values: `--dim` (opacity of an item that is not in focus), `--dim-line` (of a line), `--dim-filter` (a `grayscale()` that greys it out) and `--dash` (the `stroke-dasharray` of a dashed line); `size.stroke-thin` is a resting line's width. `tokens.py` validates each form. A type uses these rather than writing its own numbers.

**Palette slots.** Diagram data stores a slot (`"1"`..`"9"`; 9 is the neutral grey), never a hex. Each slot has a soft tone (fills) and a strong tone (lines, accents) per mode, plus the derived roles `--sw-<n>-fill|ink|line|solid|on-solid` and `--sw-<n>-tint` (the fill mixed 60 % toward `node-bg` by `tokens.py`, so every theme has it and `sw-*-ink` on `sw-*-tint` is a contrast pair; `--sw-tint` in a `[data-sw]` scope, for a quieter filled shape). `setSwatch(el, slot)` in `shell.js` sets `data-sw`, and the `[data-sw]` rules in the swatch component map the roles. A custom hex that matches no slot is drawn with a run-time derivation that no contrast check covers, and the audits warn about it. Old hex values and frame names are read as slots (`color_slot()`, `colorSlot()`).

**Text styles.** `type.styles` (`title`, `label`, `detail`, `caption`, `overline`, `code`, `control`) become `--t-<style>-*` properties and `.t-*` classes, built on the `type.size` scale. Text widths that engines and audits estimate come only from `TOKENS.font.metrics` (average character width per style, see `METRICS` in `scripts/measure_font.py`), in the page, the ERD worker, Node and headless Chrome alike.

**Icons.** One registry, see Icons below: `{{icon:name}}` in templates, `ui.icon(name)` in scripts.

**Themes.** Lookup, first match wins: `--theme <file>`, the theme stored in the page being updated (`<script id="diagram-theme">` after the data block; a page built with the default theme stores none), `.ultimate-diagram/theme.json` in the current directory, then the default. `scripts/extract_tokens.py` makes a theme from a website (`--url`) or from a partial file the agent wrote from a brand guide (`--from`, schema in `references/theme.md`); `--complete` derives the missing keys and the dark set, builds the palette, runs `measure_font.py` and moves any colour that fails contrast along OKLCH lightness. `scripts/measure_font.py` measures the theme font in headless Chrome (`--write`, `--check`). `scripts/contrast.py` is the WCAG maths behind `dev/check_contrast.py` and the `contrast` pair list in the tokens. `layout_engine.py --extract-theme page.html` writes out the theme a page carries.

### New diagram type checklist

- No `:root` block and no `--name:` declaration in the type's CSS. Tokens live in `assets/tokens/default.json` only.
- No literal colour, `font-size`, `font-weight`, `line-height`, `letter-spacing`, `font-family`, radius or shadow in the type's CSS or JS. Use `var(--...)` tokens. SVG attributes that cannot take `var()` (a shape's `rx`) are the only exception, and the engines read those numbers.
- Reuse the shared components before writing a rule (`.btn`, `.confirm` through `ui.confirm`, `.note` through `ui.noteCard`, `.edge-label`, `.frame-tag`, `.hint`); a part two types need goes into `assets/components/`.
- Every piece of text has a text style (`.t-*` or `--t-*`); the type never sets size, weight, line height or family itself. Text that shrinks to fit stops at `TOKENS.type.fitMin` (`fitMinOverview` for a zoomed-out overview).
- Icons come from the registry. A new icon is added to `assets/icons/default.json` with its licence source in `assets/icons/LICENSE` (or said to be drawn for this skill), then drawn with `{{icon:name}}` or `ui.icon(name)`. The header icon is the entry `type-<type>`. No pasted `<svg>` icon markup.
- Text widths only through `TOKENS.font.metrics`. A new text style the engine measures needs a new metric key, its mapping and headroom factor in `METRICS` in `scripts/measure_font.py`, a value in `assets/tokens/default.json`, and a re-measured `measure_font.py --check` for the default and for `dev/fixtures/themes/*.json`. The engine and the audit read the key and have no literal fallback.
- Every new colour pair the type draws is added to `contrast` in `assets/tokens/default.json` (`[foreground, background, minimum]`, 4.5 for text, 3 for lines and controls). Colours a type needs become `color` tokens, never values in the type.
- Controls are at least 24 x 24 px (WCAG 2.5.8) and show the focus ring (`--focus-ring`). Colour is never the only cue.
- Add fixtures, then run: `python dev/check_tokens.py --phase 4`, `python dev/check_contrast.py --strict`, `python dev/check_themes.py` (every fixture under every theme in `dev/fixtures/themes/`, including the dark-first, wide-font `test-brand.json`: a type that ignores tokens fails here), and `python scripts/render_screenshot.py --input <page>` with axe-core installed (`npm install`) in both modes.

## Shared components

`assets/components/` holds the parts every type reuses, one stylesheet each. `assemble_page()` joins them in `COMPONENTS` order (`layout_engine.py`) into `{{COMPONENTS_CSS}}`, so the cascade is tokens, components, shell, type. A type's stylesheet keeps only what that type alone draws (a decision diamond, a lifeline, a table row, a crow's-foot glyph) and still uses tokens only.

A new type uses these before it writes any CSS or markup of its own: a delete that needs a confirmation calls `ui.confirm`, a note is a `.note` built by `ui.noteCard`, a label on a line is an `.edge-label`, a prompt is a `.hint`. When two types need the same new thing, it goes into `assets/components/` (and `COMPONENTS`), not into either type.

## Icons

Every icon is one entry in `assets/icons/default.json` (`{"_license": ..., "icons": {name: inner SVG}}`), drawn once on a 24 x 24 grid with stroke and no fill. Pages never hold icon markup of their own; the tokens say how an icon is drawn (`icon` in `assets/tokens/default.json`: the size names `xs sm md lg xl tile` as px and as `--icon-<name>`, `stroke` 2, `strokeFine` 1.75 for large or dense icons, `strokeBold` 2.5 for tiny ones, `cap` and `join` round) and colour is always `currentColor`.

- **In a template** (`shell.html`, `toolbar.html`, `stage.html`, `chrome.html`, help files): `{{icon:trash}}`, `{{icon:trash:xs}}` or `{{icon:shape-process:tile:fine}}`. `assemble_page()` expands it to the `<svg>`, so the page does no work at start-up. A type's header icon is `{{icon:type-<type>:xl}}`, built from its name.
- **In a script**: `ui.icon('trash', { size, fine, bold, class })` returns the `<svg>` text and `ui.iconEl(...)` an element. The registry is the page's `ICONS`, the icon tokens are `TOKENS.icon`. A lane's `icon` is any registry name, so the 25 names in `references/types/flowchart.md` ("Lane icons", the agent's menu) must stay in the registry; saved diagrams store them.
- **Not icons**: the diagram's own drawing (shapes, markers, the crow's-foot glyphs, the SVG and Mermaid export strings) is drawn by the renderer in its own coordinates and stays in the type. `check_tokens.py --phase 4` flags only an inline `<svg` on the icon grid (`viewBox="0 0 24 24"`), a `{{icon:name}}` or `ui.icon('name')` whose name is missing from the registry, and a lane-icon name in the reference table that the registry lacks.
- **Another icon set**: `icon.set` in a theme names a file in `assets/icons/` with the same shape. A name the set lacks falls back to the default drawing, and the loader accepts only self-closing shape elements with a short list of attributes.
- **Adding an icon**: add the entry (draw it, or take it from an open-licensed set and add its notice to `assets/icons/LICENSE`), then use it by name.

`assemble_page()` in `layout_engine.py` fills the placeholders in one pass and writes a single standalone HTML file (`--target file`; `--target artifact` uses `assemble_artifact()`, see [claude.ai Artifact target](#claudeai-artifact-target)). JSON key `diagramType` selects the type folder; a file without it is a `flowchart`. `SUPPORTED_TYPES` lists the types that have assets and a reference.

## Plugin interface

A type's `<type>.js` ends by calling `registerDiagramPlugin({...})`. The shell calls only these members:

| Member | Purpose |
|---|---|
| `id`, `defaultTitle` | Name used for default file name and untitled diagrams |
| `contentEl` | Element whose size is fitted/panned |
| `report` | CSS selectors the render report scans: `node`, `label`, `labelText`, `nodeText`. Elements must carry `data-node-id` / `data-edge-id`. |
| `render()` | Draw `chartData` |
| `tidy()` (optional) | The Tidy button: the plugin lays out, renders and records the undo step itself (it may run the engine in a Web Worker and finish later). Missing means the shell calls `layoutDiagram(chartData)`, `render()` and `updateStatus(true)`. The ERD uses it (see ERD layout and curves) |
| `tidyResult()` | Publish positions as `<script id="tidy-result">` (used by `?tidy` and the parity check) |
| `isBackground(el)` | True for blank canvas, so a drag pans instead of selecting |
| `clearSelection()`, `cancelInteraction()`, `deleteSelection()` | Selection and Escape/Delete handling; `cancelInteraction()` returns true if it cancelled something |
| `hasSelection()` (optional) | True when `deleteSelection()` would delete something: shows the dock's Delete button |
| `selectInRect(clientRect, mode, start)` (optional) | Shift + drag on blank canvas draws a selection box (`.marquee`) instead of panning, and the shell calls this on every move so the selection previews live: select what the box (client coordinates) touches. `mode` is `replace`, or `toggle` with Ctrl/Cmd held; `start` is true on a box's first call. Missing means Shift + drag pans. Off in present mode. The flowchart uses it for multi-select. |
| `selectAll()` (optional) | Ctrl/Cmd + A outside a text field. Missing means the browser's own. Off in present mode. |
| `toDisk(data)` (optional) | Returns a new object to write into the page's data block (the [disk format](#disk-format)); must not mutate `chartData`. Missing means the block holds the in-memory model as is. |
| `fromDisk(data)` (optional) | Inverse of `toDisk`: the in-memory model from the data block. Missing means identity (the sequence plugin needs none). |
| `toMermaid(data, opts)` and `fromMermaid(text)` (optional, both or none) | The Mermaid writer and reader of the type (`assets/types/<type>/mermaid.js`, with the shared `assets/shell/mermaid-flow.js`; plain scripts joined into the page through `{{MERMAID_JS}}`, before the type script, so their globals must not clash with the plugin's: all use the `mmd`, `MMD_` or `ucm` prefix, plus `fromMermaid`, `toMermaid`). The plugin just registers the two functions. The shell shows Export › Copy › Mermaid when `toMermaid` exists (`syncCopyMenu()`, called again from `registerDiagramPlugin`) and passes it the saved form of the data (`toDisk(chartData)` without `layout`, lane colours put back) and `{ palette }`, the page theme's eight slot colours. The More menu's Paste Mermaid item (`#btn-more` › `#menu-import-mermaid`) and canvas paste (`Ctrl+V` outside text fields) read text with `fromMermaid`, refuse another diagram type, run `fromDisk`, lay the diagram out fresh (`placeImported()` / `render()`), and record one undo step; the reader's warnings and notes are listed in the bubble afterwards. |
| `placeImported()` (optional) | Called after an import, before `render()`, to lay out imported items (for example, ERD runs `layoutDiagram` on unplaced tables). |
| `contentOverflow()` (optional) | `{left, top, right, bottom}`: unscaled px that content reaches past `contentEl`'s edges, so Fit and the screenshot crop include it. The flowchart reports notes on show that sit in the margin. |
| `eachTab(fn)` (optional) | Visits every tab of a type that has tabs (the flowchart's subprocess flows), calling `fn(name)` on each, then returns to the tab the person was on. The Export menu's "SVG images, every tab" item (`data-export="svg-all"`, hidden until the plugin shows it) writes one SVG per tab through it. |
| `onViewChange()` (optional) | Called after every pan/zoom. The flowchart uses it to float a lane name pill at the visible top-left of each lane once the header column is panned out of view. While an export reads computed styles the shell sets `body.exporting`, so view-dependent styles can reset there. |

Plugins share the shell's scope: `chartData`, `scale`/`panX`/`panY`, `viewport`, `stage`, `updateStatus()`, `fitView()`.

Undo/redo lives in the shell: each `updateStatus(true)` snapshots `chartData` (as JSON) onto the history, and undo swaps `chartData` for the previous snapshot and calls `render()`. A plugin therefore gets undo for free if it calls `updateStatus(true)` exactly once per finished edit (on pointerup, not on every pointermove) and keeps no references into `chartData` across renders.

The sequence plugin always derives positions from its engine. The flowchart has an **auto layout** mode (on by default; the dock's Auto-Tidy switch, remembered in `localStorage`, not saved in the file). While it is on, `relayout()` (engine, render, then `updateStatus(true)`, so the edit and its re-layout are one undo step) runs after every *step* edit: adding, moving or deleting a step, and adding, reordering or deleting a lane. The exception is a shape dragged from the dock onto blank canvas: it has no arrows yet, so it stays where it is dropped (a re-layout would only throw it to the start of the flow). *Arrow* edits (connect, reconnect, delete, label) deliberately do not re-lay out: reordering steps means rewiring several arrows, and re-laying out each intermediate graph would make the diagram jump. The engine reads only structure (arrows, lane membership, lane order), not x/y, so with auto layout on a drag only chooses a lane or an arrow to insert into. With it off, the page behaves as a manual editor (drop where you like, snap guides) and only the Tidy button re-lays out.

With subprocess flows (`children` on disk) the editor still works on one flow at a time: the active tab's lanes, steps, arrows and notes are `chartData.lanes/nodes/edges/notes`, the other tabs are parked in `chartData.flows`, every lane's name, icon and colour is kept once in `chartData.actors` (copied in when a tab is left, read out when one is entered), and `chartData.tab` names the active child (`flowchart.js`, SUBPROCESS TABS; `toDisk`/`fromDisk` convert to and from the full model). Flows nest up to `MAX_FLOW_DEPTH` (4) levels, but the maps stay flat: a flow's parent is the flow holding the step whose id is its slug (`parentOf`, `depthOf`, `canNest`, `childrenOf`, `subtreeOf` in `flowchart.js`; no `parent` field). On a level-4 flow the Subprocess tile is disabled and Collapse is hidden; deleting a step removes its whole subtree (`dropChildOf`); `eachTab` and the export walk the tree depth first. The tab bar is nested folder boxes along the path to the current flow, the innermost holding its direct children only (`renderTabs`); a tab above the current flow goes back up with the step that led down selected, Alt+Up goes to the parent, and a subprocess tab has a right-click (Menu key, Shift+F10) Delete. Deleting a subprocess step that has content asks Merge into parent (`expandSubprocess`, disabled with `expandBlocker`'s reason) / Delete everything / Cancel (`confirmDeleteSub`, via `ui.confirm` with its `alt` button); a still-blank new subprocess deletes at once. A diagram without children has none of these keys. A lane height saved on disk is what the page measured, so the last lane of the parent may differ from the generated one by the room for outer loop-backs.

The flowchart selects several *steps* at once (never arrows, notes or lanes; see `MULTI-SELECT` in `flowchart.js`). `selectedNodeIds` holds the selection and `selectedNodeId` its primary step, the one clicked last, which is all that notes, the N key and note linking look at. Deleting, moving to another lane (a drag or Alt + arrow keys) and moving a run elsewhere in the flow (Alt + drag onto an arrow, or Alt + arrow keys along the flow: `moveRunIntoEdge`, which also inserts a new step dropped onto an arrow) are each one edit with one `updateStatus(true)`, so one undo step. Moving a run rewires: the arrows into it are re-pointed past it and the arrow it is dropped on is split around it. Without Alt, a drag never rewires connected steps. The selection is never saved.

## Disk format

The page's `<script id="diagram-data">` block is written for a reader (an agent opening the file), not for the engine. It sits in `<head>` straight after `<title>`, with a reading guide on line 2 and an `<!-- end diagram-data -->` marker after it, so the model is in the first lines of the file. The in-memory model (engines, renderers, audits, undo history) is unchanged; the conversion happens only where JSON is read from or written to the page:

| | In memory | On disk |
|---|---|---|
| Key order | any | fixed: flowchart `diagramType, schemaVersion, title, direction, swimlanes, showNotes, lanes, nodes, edges, notes, layout`; sequence `diagramType, schemaVersion, title, numbered, showDetails, rails, lifespans, colorKey, participants, messages, fragments, notes`; unknown keys last; erd `diagramType, schemaVersion, title, detail, showTypes, showNotes, colorKey, entities, relationships, notes, layout`; usecase `diagramType, schemaVersion, title, showRefs, showNotes, colorKey, subjects, actors, useCases, links, notes, layout` |
| Flowchart positions | node `x`/`y`, lane `height`/`color` on the objects | one trailing `layout` map keyed by id (the steps of child flows too) |
| Flowchart child flows | `children[slug]` = `{name, laneOrder, laneHeights, nodes, edges, notes}`; `lanes` is the one actor list for every tab | `children` after `notes`, each child in the key order `name, laneOrder, laneHeights, nodes, edges, notes`; its steps in flow order and its positions in `layout`; `laneHeights` stays in the child |
| Colours | a slot (`"1"`..`"9"`) or a custom hex on lane, participant, frame and table `color`; `colorKey` keyed by slot | slots; old palette hex and frame names are read as slots, a custom hex is written unchanged (`color_slot`, `colorSlot`) |
| Flowchart node order | any | flow order: `(x, lane index, y)`. `x` runs along the flow in both directions, so no graph walk is needed. `check_golden.py` proves the order never changes a layout |
| Editor-generated ids (`n_<timestamp>`, `c_`, `e_`, `lane_`) | kept for the session | renamed: `n_<label slug>`, `c_<letter>_in/out`, next free `e<N>`, `lane-<name slug>`; references follow. Authored ids are never touched |
| Sequence editor ids (`p_<timestamp>_<k>`, `m_`, `f_`, `n_`) | kept for the session | renamed: `p_<name slug>`, next free `m<N>`, `f<N>`, `n<N>`; every reference (`from`/`to`, `elseAt`, `branches[].at`, note `over`/`after`/`before`) follows |
| ERD positions | entity `x`/`y` (absolute top-left) on the objects | one trailing `layout` map `{tableId: {x, y}}`, tables only, in table order; needed because tables are placed by hand and by edits, never re-laid out except by Tidy. `fromDisk` puts them back. ERD `schemaVersion` is 3. Any other version (a v2 block with `groups`, or v1) has its `layout`, `direction`, `groups` and `group` fields dropped on read, each group's colour becomes the `color` of its tables and its name a `colorKey` entry, and the page and `--layout` lay the diagram out afresh |
| ERD derived fields | `entities[].box`, `relationships[].curve`, `points` and `labelBox`, `canvas` (`width, height, crossings, length, hits`), `_loose`, `_band` (engine output) | not saved: `render()` runs `layoutDiagram` when a table has no `x`/`y`, else `routeDiagram` |
| ERD editor ids (`t_<timestamp>[_k]`, `r_`, `n_`) | kept for the session | renamed: tables `<name slug>` (suffix `_2`... when taken), relationships `r<N>`, notes `n<N>`; `from`/`to` and a note's `entities` follow. Authored ids are never touched |
| Use case positions | actor and use case `x`/`y` (absolute top-left) on the objects | one trailing `layout` map `{id: {x, y}}`, actors then use cases, in array order; manual placement survives Save (as the ERD). `schemaVersion` is 1; a block with another version has its `layout` dropped on read. The codec spec is the comment block above `usecase_to_disk` in `scripts/disk_format.py` |

**Reading guide line numbers.** Line 2 names the block's real line range ("on lines S-E of this file. Read lines 1-E only (offset 1, limit E)"), because an agent's file tools work in line ranges and a whole-file read of a ~500 KB page fails before the agent sees any text. The numbers are stamped from the finished text by `stamp_reading_guide()` (in `assemble_page()`) and `stampReadingGuide()` (on Save); only the guide line is rewritten. A hand edit of the JSON leaves them stale: the guide tells the reader to trust the end marker over them, and `--verify` warns. No huge lines may sit just past the block (the fonts used to be inlined there), so a read that overshoots the end marker lands on ordinary CSS. `build_examples.py --check` checks all of this.

Two implementations exist: `scripts/disk_format.py` (`DISK_CODECS`, used by `assemble_page()`, `extract_data_from_html()` and `--extract`) and the plugins' `toDisk`/`fromDisk` plus the shell's `formatJson`. They must agree byte for byte: `e2e_shell.mjs`, `e2e_sequence.mjs` and `e2e_erd.mjs` save a generated page without edits and compare the block. `--extract` prints Mermaid by default, or `--json` for the authoring JSON (the disk model without `layout`). On Save the shell also writes the diagram title into `<title>` and the header `<h1>`.

## claude.ai Artifact target

`layout_engine.py --target artifact -o <dir-or-index.html>` calls `assemble_artifact()` to write four split files into the target directory (`index.html`, `diagram.json`, `app.css`, `app.js`) instead of one monolithic page, keeping `--target file` (`assemble_page()`) untouched:

- **`index.html`:** built from the template derived from `shell.html`: the exact Artifact skeleton (`ARTIFACT_HEAD`: doctype, charset, viewport, and reset `<style>` in `<head>`, then `<body>`), `<title>`, an agent comment pointing to `diagram.json`, optional `<script id="diagram-theme">`, Google Fonts links, `<link rel="stylesheet" href="app.css">`, body mount and toolbar/chrome markup, `<script src="app.js"></script>`, `ARTIFACT_END_MARKER`, and `ARTIFACT_TAIL` (`</body></html>`). Nothing else may sit in `<head>`.
- **`diagram.json`:** the diagram model in disk format (`_readme`, `schemaVersion`, `layout` map). `--extract` accepts either an `.html` page or `diagram.json`.
- **`app.css` and `app.js`:** `app.css` joins `{{TOKENS_CSS}}`, `{{COMPONENTS_CSS}}`, `shell.css`, and `<type>.css`; `app.js` joins `{{TOKENS_JS}}`, `shell.js`, `//@engine-begin`..`//@engine-end` wrapping `engine.js`, `<type>.js`, and the `loadInitialData()` boot call. `find_external_refs()` checks `index.html`, `app.css`, and `app.js`.
- **Dual-mode boot and Web Worker (`shell.js`):** `shell.js` detects `artifactShaped` via `document.querySelector('body > title') !== null` while capturing the unrendered body markup before `plugin.render()` for HTML export. `loadInitialData()` reads `#diagram-data` synchronously when present (`--target file` or an exported `.html`), or `await fetch('diagram.json')` in split artifacts, and sets both `chartTitleEl.textContent` and `document.title` from `chartData.title || plugin.defaultTitle`. `loadEngineSource()` slices `//@engine-begin`..`//@engine-end` from `document.currentScript.textContent` (inline builds) or fetches `document.currentScript.src` (`app.js` in split builds), so `assets/types/erd/erd.js`'s background layout Web Worker works in both builds without any artifact-specific code in `erd.js`.
- **Files-form `publish` and `Export > HTML file` (`shell.js`):** inside an artifact, Save (`publishToArtifact()`) calls `claude.use("artifact")` in its files form, `artifactApi.publish({"diagram.json": updatedJson})` (with per-file `ifMatch` when supported by the runtime contract), never rebuilding or re-uploading `index.html`, `app.css`, or `app.js`. Because nothing in the saving view is rebuilt, `reloadExpected` is not set on Save; the view keeps running with no reload, preserving selection and undo history in memory (`conflict` still triggers reload handling). View-only viewers and `capability_disabled` errors do not add a separate `btn-download-html` button; **Export > HTML file (editable)** fetches `app.css` and `app.js` and inlines them with the captured unrendered body markup, current `<script id="diagram-data">`, optional `#diagram-theme`, and `stampReadingGuide()` into `shell.html`'s `<head>`/`<body>` layout as a self-contained `--target file` download.
- **Headless Chrome and `--keep-layout`:** Chromium `fetch()` rejects `file://` URLs, so `scripts/render_screenshot.py` and `dev/cdp.mjs` serve split artifact directories over a local loopback HTTP server when opening them in headless Chrome. With `--keep-layout`, `layout_engine.py` and `scripts/run_engine.mjs` (`--keep`) preserve saved `x`/`y` positions for types whose `engine.js` defines no `routeDiagram` (such as `flowchart`, which routes edges in the renderer) rather than calling `choose_flowchart_direction` or `layoutDiagram`.
- **Type independence:** `assets/types/<type>/engine.js` and `<type>.js` remain completely independent of artifacts; layout engines and type plugins never inspect or branch on artifact packaging.

## One engine per type

Layout lives only in `assets/types/<type>/engine.js`. The page runs it for the Auto-Tidy button; `--layout` runs the same file through Node.js (or headless Chrome if Node is missing), so there is nothing to keep in sync. The Python `--verify` audit routes edges itself to check the result; it never computes layout. If `FlowchartAudit` and the page's renderer ever disagree on a route, trust the render report and fix the audit.

### ERD layout and curves

The ER diagram lays out and draws its lines in `engine.js`, not in the renderer as the flowchart does: the line ports sit on the four sides of a table, whose sizes follow from the engine's own row height, so no DOM is needed and `audit_erd.py` can check exactly what is drawn. `layoutDiagram` is a graph layout (D4 of the v3 plan): shortest-path distances on the undirected FK graph (same-coloured tables count as slightly closer), a deterministic seed with the highest-degree table in the centre, stress majorization, an edge-node repulsion pass so curves pass beside tables, rectangle-aware overlap removal, scaling toward the view's aspect, and packing of disconnected components. It tries a few mirrored and rotated variants and keeps the one with the fewest curve-over-table hits, then the fewest crossings, then the shortest length. Above `ER.LITE` (10) tables the search is lighter (6 variants instead of 18, one refined with a shorter schedule, no final polish): 30 tables lay out in about 2.6 s and 60 in about 10 s, and a large schema may keep one curve over a table or its hubs off-centre. Each relationship is then one cubic Bezier (D3): each end sits on the side that faces the other table, several ends on one side spread along it ordered by where the other end lies, and the curve leaves each port at right angles to the side. The result is stored as `relationships[].curve` (four control points) and `points` (17 sampled points, used for crossings and the audit). `routeDiagram` redraws the curves from saved positions without moving tables; the page calls it when positions already exist (loading a saved v3 page, a hand drag with Auto-Tidy off), and `layoutDiagram(data, { warm: true })` starts from the current positions after a structural edit with Auto-Tidy on (D5). A diagram of 12 tables or more is laid out in a Web Worker so the page does not freeze (a cold layout of 30 tables takes about 2.6 s, 60 tables about 10 s): `erd.js` builds the worker from the engine's own source via the shell's `loadEngineSource()` helper (which slices `//@engine-begin`..`//@engine-end` from the inline script or fetches the external `app.js`), posts the model, and applies the returned positions and curves as one undo step. While it runs a status hint shows and `body[data-erd-busy]` is set; pan and zoom work, and a result is dropped when the model changed meanwhile (the next layout or Tidy replaces it). Without `Worker`, `Blob` or the marker lines (a CSP, an artifact host that rewrites scripts), or under `?tidy`/`?report`, the layout runs synchronously. A page opened without positions shows a provisional grid until the worker answers. There is no direction: a schema has no reading order, and `--layout` calls the engine once. There are no groups: domains are shown by per-table `color`. The ERD draws no orthogonal arrows, so it does not call the shared router (`assets/shell/ortho-router.js`), which ships in its page only because every type's `ENGINE_JS` carries it.

### Flowchart direction (`"direction": "TB"`)

A top-to-bottom flowchart uses the same engine, router and audit as a left-to-right one. Node `x`/`y` are always in **flow terms**: `x` runs along the flow (from the start of the lane track) and `y` across the lane (from its edge). Only the sizes change:
- `engine.js` `useDirection(data)` switches `LE` to `LE_PROFILES.TB`. Nodes are 96px along the flow (a decision's height; a step is centred in it) and 144px across it.
- `FlowchartAudit` picks the matching sizes.
- The renderer turns flow terms into the screen: n.x becomes the screen y and n.y the screen x (`placeNodeEl`, `flowPoint`, `flowToContainer`).
- `routeEdgesOrthogonal` (`assets/shell/ortho-router.js`, called by the flowchart's `computeAllEdgeRoutes`) transposes the node boxes before the route search and the polylines back afterwards (step 5e), so every routing rule is written once, for left to right.

## Keeping `references/reading.md` current

`references/reading.md` is the only description the agent has of a type's JSON when it explains an existing diagram, and nothing tests it. Whenever a change breaks a field's name, meaning or values in a type's saved JSON (a rename, a removed or reinterpreted field, a new `schemaVersion`), update that type's section in `reading.md` in the same change, next to the schema in `references/types/<type>.md` and the codec in `scripts/disk_format.py`.

## Adding a type

1. `assets/types/<type>/` with the files above and a reference in `references/types/<type>.md`, and the registry entry `type-<type>` in `assets/icons/default.json` (the header icon: there is no `icon.html`).
2. Add the type to `SUPPORTED_TYPES` and `SKILL.md`'s type table, and a section to `references/reading.md`.
3. Write `engine.js` defining `layoutDiagram(data)` (pure, no DOM) and an audit class with `title`, `verify_collisions()`, `summary_lines()` and `pass_line()`; register it in `AUDITS` in `layout_engine.py`.
4. Follow the [new diagram type checklist](#new-diagram-type-checklist) for everything visual.
5. Add fixtures under `dev/fixtures/<type>/`, freeze goldens with `python dev/check_golden.py --update`, and run the tests below.

The `sequence` type is the reference for a type that shares nothing with the flowchart except the shell: its own renderer, engine, audit and reference. The `erd` type is the third: its own engine, audit and renderer too (it did not need the flowchart's router, see below). The `usecase` type is the fourth, built the same way (engine, `audit_usecase.py` in `AUDITS`, its own codec). The state diagram is planned; when it needs the flowchart's orthogonal router or layered ranking, extract those into shared modules at that point rather than speculatively.
