# Brief: Card checkout with 3-D Secure, fraud scoring, inventory and fulfilment (sequence diagram)

Participants: Shopper, Web App, API Gateway, Auth Service, Cart Service, Pricing Service, Inventory Service, Inventory DB, Order Service, Orders DB, Fraud Service, Payment Service, Card Network (external), Issuer ACS (external), Event Bus, Email Service, Warehouse System (external).

Login phase: The Shopper opens checkout in the Web App. The Web App sends the session token to the API Gateway, which asks the Auth Service to validate it; the Auth Service returns the user id or 401. On 401 the Web App shows the login page, the Shopper submits credentials, the Auth Service checks them and issues a new token (up to 3 attempts, then the account locks for 15 minutes).

Cart phase: The Web App asks the Cart Service for the cart. For each line item the Cart Service asks the Pricing Service for the current price and promotions; the Pricing Service returns the price. The Cart Service applies a voucher if present (optional), recalculates totals, and returns the cart. The Cart Service asks the Inventory Service to reserve stock; the Inventory Service writes a reservation to the Inventory DB with a 15-minute TTL. If any item is out of stock, the Inventory Service returns a shortage and the Web App asks the Shopper to remove or back-order the item.

Order phase: The Web App posts the order to the Order Service through the API Gateway. The Order Service checks the idempotency key, writes the order as PENDING to the Orders DB, and asks the Fraud Service for a risk score (amount, device fingerprint, IP, history). Score below 300: proceed. Score 300 to 700: require 3-D Secure. Score above 700: reject the order and release the reservation.

Payment phase: The Order Service asks the Payment Service to authorise the amount. The Payment Service sends the authorisation to the Card Network. If 3-D Secure is required, the Card Network returns a challenge URL; the Web App redirects the Shopper to the Issuer ACS, the Shopper completes the challenge, the Issuer ACS returns the result to the Card Network, which then returns the authorisation result. Approved: Payment Service returns auth code. Declined: Payment Service returns the decline reason, the Order Service marks the order FAILED and asks Inventory Service to release the reservation, and the Web App shows the error. The Payment Service retries network timeouts up to 2 times with exponential backoff.

Confirmation phase: On approval the Order Service updates the order to CONFIRMED, asks the Inventory Service to commit the reservation (Inventory DB decrements stock), and publishes OrderConfirmed to the Event Bus asynchronously. The Email Service consumes the event and sends the confirmation email. The Warehouse System consumes the event, creates a pick list and later publishes Shipped with a tracking number; the Order Service consumes Shipped, updates the order and the Email Service sends a shipping notice. The Web App shows the confirmation page with the order number.

Rules: card data never touches the Web App (tokenised by Payment Service); every service call carries a correlation id; reservations expire automatically after 15 minutes.
