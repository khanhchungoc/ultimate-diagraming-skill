# C4 Diagram (`diagramType: "c4"`)

Use for a system landscape in the C4 model: the people who use your software, the software systems around them and, one level down, the containers (apps, services, databases, queues) inside one system. Level 1 is system context, Level 2 is containers. Not for the order of steps (use `flowchart` or `sequence`), not for tables (use `erd`) and not for use cases. Level 3 (components) is not supported in v1. Positions, box sizes and arrow routes are computed by the tooling; author only the logical JSON.

This type is JSON, not Mermaid. The page shows it, collapses and expands groups, searches, lets the reader edit it by hand and saves (see Editing in the page).

## JSON

This is a complete diagram; no other file to read. Key order: `diagramType, schemaVersion, title, arrange, showTech, showNotes, colorKey, groups, elements, relations, notes`. Do not write `layout`, sizes or any `_` field.

```json
{
  "diagramType": "c4",
  "schemaVersion": 1,
  "title": "ShopCo system landscape",
  "colorKey": { "1": "People", "2": "ShopCo systems" },
  "groups": [
    { "id": "shopco", "name": "ShopCo", "kind": "boundary" },
    { "id": "platform", "name": "Order Platform", "kind": "system", "parent": "shopco", "collapsed": false },
    { "id": "third", "name": "Third-party services", "kind": "boundary" }
  ],
  "elements": [
    { "id": "cust", "kind": "person", "name": "Customer", "description": "Buys products online", "color": "1" },
    { "id": "web", "kind": "container", "name": "Web App", "tech": "React", "group": "platform", "icon": "browser" },
    { "id": "api", "kind": "container", "name": "API Gateway", "tech": "Node.js, REST", "group": "platform", "icon": "gateway" },
    { "id": "orddb", "kind": "database", "name": "Order DB", "tech": "PostgreSQL", "group": "platform", "icon": "database" },
    { "id": "crm", "kind": "system", "name": "CRM", "description": "Customer records", "color": "2", "group": "shopco" },
    { "id": "pay", "kind": "external", "name": "Payment Provider", "group": "third", "icon": "credit-card" }
  ],
  "relations": [
    { "from": "cust", "to": "web", "label": "Browses and orders", "tech": "HTTPS" },
    { "from": "web", "to": "api", "label": "Calls", "tech": "JSON/HTTPS" },
    { "from": "api", "to": "orddb", "label": "Reads and writes orders", "tech": "SQL" },
    { "from": "api", "to": "pay", "label": "Charges cards", "tech": "REST", "async": false },
    { "from": "api", "to": "crm", "label": "Syncs customers", "tech": "REST", "async": true }
  ],
  "notes": [
    { "id": "n1", "text": "Open the Order Platform to see its containers.", "groups": ["platform"] }
  ]
}
```

A larger, audited example is [references/examples/example-c4.json](../examples/example-c4.json).

- **Elements** (`id`, `kind`, `name`, optional `description`, `tech`, `group`, `icon`, `color`, `core`, `side`). `kind` is `person` (a role, never a named individual), `system` (a software system), `container`, `component` (not used in v1), `database`, `queue` or `external` (a system you do not own). The kind sets the default shape and icon. `description` is one short line of what it is or does; `tech` is the technology of a container (`"Node.js, REST"`). An element belongs to at most one `group`. `core: true` marks a centre of the diagram; `side` (`N`, `S`, `E`, `W`) asks for the side of the centre it sits on.
- **Groups** (`id`, `name`, `kind`, optional `parent`, `collapsed`, `core`, `side`, `color`). `kind` is `boundary` (an ownership or trust frame such as "Third-party services") or `system` (a software system whose inside is its containers). `parent` nests a group in another. `core` and `side` work as on an element (a group can be the centre). `color` is a palette slot (`"1"` to `"9"`) or a hex; the frame takes that colour, and `colorKey` names it. Never use kind `container`: it is rejected until Level 3.
- **Relations** (`from`, `to` element ids; `label` required; optional `tech`, `async`). Relations join elements, never groups, and never an element to itself. Two elements in the same group or layer may be related (see Links inside a group). `async: true` draws a dashed line.
- **Notes** (`id`, `text`, `elements` and/or `groups`): 120 characters at most; use sparingly.
- **Ids** are short and lower case, unique across groups and elements (`api`, `orddb`).
- **Colour**: `color` (on an element or a group) is a palette slot `"1"` to `"9"` named in `colorKey` (shown as a legend). Colour people one slot and your own systems another; leave the rest to the kind defaults.

## Editing in the page

The reader can change the diagram by hand: add a person, system, container, database, queue, external system or group from the dock; rename (double-click, F2 or Enter); connect two elements (drag from a port, or Connect) and type the required label; set kind, icon, colour, group, centre (`core`) and side, and an arrow's label, technology, async and direction; delete; undo and redo. Auto-Tidy is always on: after every add, connect, delete, group change or collapse the page drops positions and lays the diagram out again, so write nothing about where things sit. On Save, the editor's ids (`e_<timestamp>`, `g_<timestamp>`) are renamed to name slugs (unique; relations, `group`, `parent`, notes, `core` and `side` follow), and every `_` field is dropped. Not editable yet: moving boxes by dragging, notes, icon packs (`logo:` names) and Mermaid import or export.

## Arrange (the layout)

`arrange` is one of `surround`, `flow` or `layers`. Leave it out and the page uses `surround` when any element or group has `core: true`, otherwise `flow`. Nothing is picked as the centre for you.

- **`surround`**: the items marked `core` (one, two, four, or a group) sit in the middle; everything else rings round them by how many links away it is. Mark only real centres, and give each a relation.
- **`flow`**: no centre; the layout starts from the items nobody points at and flows down in layers. Use it for a service mesh or a pipeline.
- **`layers`**: each top-level group is a horizontal band, stacked in the order written (Experience, Services, Platform, External). Every element must sit in a top-level group (a child group counts). Relate bands that touch; a relation that skips a band warns. `core` has no effect here.
- `side` is a hint, not an order: use it only when the default side is wrong (a carrier always to the west).

```json
{ "arrange": "layers",
  "groups": [ { "id": "exp", "name": "Experience", "kind": "boundary", "color": "1" },
              { "id": "svc", "name": "Services", "kind": "boundary", "color": "2" } ],
  "elements": [ { "id": "web", "kind": "system", "name": "Storefront", "group": "exp" },
                { "id": "orders", "kind": "system", "name": "Orders", "group": "svc" },
                { "id": "bill", "kind": "system", "name": "Billing", "group": "svc" } ],
  "relations": [ { "from": "web", "to": "orders", "label": "Orders", "tech": "HTTPS" },
                 { "from": "orders", "to": "bill", "label": "Charges", "tech": "gRPC" } ] }
```

## Links inside a group

Members of one group may be related, including members that are not next to each other (a chain `web, api, orders, db`, or `cart` to a member two places along). The page lays a group's members in a row when the links join neighbours, and as a small flow when a link would cross a sibling; you write the same JSON either way. A collapsed group hides its inner links.

## Icons

Set `icon` only when the default for the kind is not specific enough. Use generic icon names only, from `assets/icons/default.json`: `browser`, `mobile`, `monitor`, `gateway`, `api`, `server`, `function`, `cluster`, `container`, `cache`, `cdn`, `storage`, `database`, `queue`, `cloud`, `lock`, `key`, `shield`, `mail`, `bell`, `credit-card`, `truck`, `globe`, `cpu`, `headset`, `user`, `users`. Never invent a name.

Technology logos are written `logo:<slug>` (such as `logo:postgresql`) or `logo:<pack>/<name>` (`logo:aws/s3`). They come from optional packs the user installs, so do not rely on them: a missing pack falls back to the element's generic icon and the audit warns once per element. Write `logo:` names only when the user asks for them or the pack is known to be installed.

## Writing rules

Work from the broad level down. Write the whole model once.

1. **Level 1: people and systems.** List the people (roles) who use the landscape and the software systems around them. Your own systems are `system`; systems you do not own (payment, email, identity) are `external`. Put each element in the boundary that owns it: your systems in one `boundary`, third parties in a second ("Third-party services"). An `external` is never inside a `system` group.
2. **Level 2: containers of one system.** For the system the reader needs to open, make a `system` group and put its containers in it: apps, services, `database`, `queue`. Give each a `tech`. Open one system, not all. Other systems stay a single `system` element or a collapsed `system` group.
3. **Relations.** One per real interaction, each with a `label` that says what it does (verb phrase: "Charges cards", "Sends receipts"). Every container-to-container relation gets a `tech` (REST, gRPC, AMQP, SQL). Use `async: true` for fire-and-forget links (events, queues, mail). A relation goes between the elements it really joins: a person to the app they use, not to every container behind it. Do not draw the same pair twice with the same label.
4. **Connect everything.** Every person and element has at least one relation.
5. **Choose the opening level.** `collapsed` on a `system` group is saved and decides how the page opens. Every system group collapsed opens at Level 1 (system context); one expanded opens at Level 2. A group with `collapsed: true` still holds its children in the data; the page shows them when the reader expands it.
6. **Choose the arrange.** One system the others serve: mark it `core`. Several peers: mark each `core`. A layered architecture: `arrange: "layers"` with one top-level group per layer. No centre: write neither.
7. **Check.** Every id used in `from`, `to`, `group`, `parent` exists; no group is its own ancestor; no group nests deeper than 2.

## Budgets

The audit (`scripts/audit_c4.py`) holds these numbers; do not exceed them.

| Item | Limit | Past it |
|---|---|---|
| Visible children of one group (elements and child groups) | 12 | warning: split into smaller groups |
| Visible elements in the whole diagram | 80 | info: set `collapsed: true` on system groups so it opens at Level 1 |
| Relation label | 40 characters | warning: shorten it |
| Group nesting depth (`MAX_GROUP_DEPTH`) | 2 | error |
| Groups an element is in | 1 | error |

Collapsed groups show no children, so their contents do not count as visible. Never drop a system to save space: collapse it.

## Levels

- The model is one JSON for every level. The level is only the `collapsed` state of the `system` groups.
- A collapsed `system` group draws as one system box. Relations that cross its border are drawn onto the box, one arrow per neighbour, with the count when it merges several. Expand it (the chevron in its title) to see the containers.
- To publish a Level 1 page, set `collapsed: true` on every `system` group. To publish Level 2 of one system, leave only that group expanded. The page saves `collapsed`, so it reopens where the reader left it.
- Level 3 (components inside a container) is not supported in v1: `MAX_GROUP_DEPTH` is 2, the `container` group kind is rejected, and `component` elements are not used. If the user asks for components, say so and model the containers.

## Visual checklist

Check before you finish; the page is generated, so this is for the data you wrote.

- The title says the scope ("ShopCo system landscape", "Order Platform containers").
- Each person is a role and has a relation; people are grouped by colour slot, named in `colorKey`.
- Third-party systems are `external`, in a boundary of their own, outside every `system` group.
- Every arrow has a short verb-phrase label; container links carry a `tech`; async links are marked.
- No group has more than 12 children; labels are 40 characters or fewer.
- Icons are generic names from the list above (or an installed `logo:` pack).
- `arrange` fits the story (centre, flow or layers); `core` items are real centres; in `layers` no relation skips a band.
- The `collapsed` state matches the level you mean the page to open at.

## Failure handling

- **Audit `[ERROR]`**: a model rule is broken (duplicate id, unknown id in a relation, group cycle, element in two groups, relation without a label, a relation from an element to itself, unknown `arrange`, an element outside a band in `layers`, nesting past 2, kind `container` on a group). Fix the item it names and run again.
- **Audit `[WARN]`**: fix each with a targeted edit (add the `tech`, shorten the label, connect or remove the element, move the external out of the system group, split the big group, drop an uninstalled `logo:` name, relate a `layers` band to the next one instead of skipping it, drop `core` from an item with no relation). Never rewrite the diagram.
- **Codec `ValueError`** (duplicate or unknown id, unknown kind, group cycle, unknown `arrange`, `side` not N, S, E or W, `core` not true or false, bad `color`): the JSON is malformed at the boundary; correct the named id or kind.
- **The user asks for Level 3, deployment or a dynamic view**: not in v1; say so and give Level 1 and 2.
- **A fact is missing** (a technology, a direction): leave `tech` out or the label general; do not invent it. A container link without a `tech` costs one warning.
